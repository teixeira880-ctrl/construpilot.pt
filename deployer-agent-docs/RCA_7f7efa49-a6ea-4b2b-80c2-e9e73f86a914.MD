# RCA — Assistant BTP "create a quote" hangs on "Analyse en cours" in PRODUCTION only

**Deployment:** cmrenov-ai (`44fe2224-...`) · active run `7f7efa49-a6ea-4b2b-80c2-e9e73f86a914` (redeploy, success, 2026-10-04 15:06Z)
**Frontend type:** `cloudflare` (static from R2, `/api` proxied through a Cloudflare Worker/edge to the k8s backend)
**Endpoint:** `POST /api/assistant/message/stream` (SSE, `text/event-stream`)

---

## TL;DR
The bug is **not** a missing/exhausted secret and **not** a dead pod. The backend finishes every request successfully in prod. The root cause is twofold:

1. **Production runs a completely different LLM code path than preview, and that path is not SSE-robust.** `ASSISTANT_PROVIDER` in prod is `anthropic` (preview `.env` has `openai`). This forces every turn through `engines/assistant_claude.py::run_chat_claude`, which — unlike the OpenAI path — emits **no periodic keepalive bytes** during the model's long silent prefill/reasoning gaps. Behind the Cloudflare edge, a long-lived SSE stream that goes silent for tens of seconds stalls: the browser's `reader.read()` blocks forever, so "Analyse en cours" never clears. The preview validation ("works perfectly") exercised the OpenAI path only — it never touched the code that actually runs in prod.
2. **A secondary quote-draft concurrency bug inflates the turn duration**, making the stall far more likely to trigger.

This is primarily a **Code (E1)** fix. There is also a **User** decision about the provider secret.

---

## Evidence

### The prod path is the Claude path, not the OpenAI path (proven)
- `list_secrets` with `equals`: `ASSISTANT_PROVIDER` → `matches_expected: true` for value `anthropic` (and `false` for `openai`).
- Preview source: `backend/.env` → `ASSISTANT_PROVIDER=openai`.
- `engines/assistant_fallback.py::use_fallback_now()`:
  ```python
  if primary_provider() == "anthropic":
      return True, "fournisseur principal : clé universelle"
  ```
  and `routes/assistant.py::_run_chat()` then runs `run_chat_claude(...)` and `return`s — the OpenAI streaming branch is never reached in prod.

### The backend COMPLETES in prod — it is not hanging, and no secret is missing (proven)
For the cmrenov pro account (`user_1dc6be8337e6`), every recent quote turn wrote a full result set to the prod DB (`cmrenov-ai-test_database`):
- `ai_usage` (provider=anthropic, billing=emergent) at 15:07, 15:17, 15:22, 15:27Z — real token counts (input 82k–393k, output up to 20,205).
- `assistant_msgs` (role=assistant, provider=anthropic) with the finished quote reply for each `request_id`.
- `assistant_traces` with completed step lists (e.g. steps 0→5 ending in a final text-only step).

In `run_chat_claude`, `ai_usage`/`assistant_msgs`/`save_trace` are all written **immediately before** `yield {"type":"done"}`. Their presence proves the generator reached `done`. EMERGENT_LLM_KEY + ASSISTANT_CLAUDE_MODEL_* are present/non-empty and Anthropic calls succeed. **So: not a missing secret, not an exhausted OpenAI key (that path isn't even used; admin also re-activated the OpenAI key at 15:35), not a crashed pod.** `/api/` returns 200.

### Why the UI hangs forever instead of erroring (proven by source)
Frontend `src/lib/assistantStream.js`:
- Clears the spinner only on `event.type === "done"`.
- If the stream **closes** without `done`, it throws `"Connexion interrompue avant la fin de la réponse."` (an error, not an infinite spinner).
- An **indefinite** "Analyse en cours" therefore means `reader.read()` never returns and never closes → bytes are not arriving AND the connection is not closed. That is the signature of an intermediary **buffering/holding a silent long-lived SSE connection**, i.e. the Cloudflare edge on a stream that produced no bytes for a long stretch.

### The Claude path has no keepalive; the OpenAI path does (proven by source)
- OpenAI path (`_run_chat`, prod-unused) pings during silent waits:
  ```python
  done, _ = await asyncio.wait({nxt}, timeout=8)
  if not done:
      yield {"type": "ping"}
      continue
  ```
- Claude path (`run_chat_claude`, prod-active) only yields on real `TextDelta`/`ToolCallStart` events:
  ```python
  async for ev in chat.stream_message(user_msg):
      if isinstance(ev, TextDelta): yield {"type":"delta", ...}
      elif isinstance(ev, ToolCallStart): yield {"type":"status", ...}
      ...
  ```
  Between tool steps, each `chat.stream_message` call re-prefills the full (growing) context — the traces show 320k–393k **summed** input tokens across 6 steps, i.e. ~50k–90k-token prefills per step on `claude-sonnet-4-6`. That is tens of seconds of **silence** per step with zero bytes on the wire. (`_tool_turn`'s 8s status only covers tool *execution*, not the model's prefill/reasoning.) `X-Accel-Buffering: no` / `Cache-Control: no-cache` are set on the `StreamingResponse`, but `X-Accel-Buffering` is an nginx hint and does not govern the Cloudflare Worker edge in this frontend topology.

### Secondary bug — quote-draft concurrency conflicts (proven by stored replies)
The 15:22 and 15:27 assistant replies contain, verbatim:
- *"Le système détecte des modifications concurrentes sur ce devis."*
- *"verrou persistant sur les mises à jour"*, *"les deux outils — mise à jour et création — échouent"*.
Traces show the model looping read_quote_draft → update_quote_draft → read → update (steps 0–5/6) because `update_quote_draft`/`create_quote_draft` keep failing an optimistic-lock / concurrency check. This multiplies steps, context size (hence the 390k input tokens) and total duration — directly worsening the silent-SSE stall.

## Adjudicating the three hypotheses you raised
1. **Edge SSE buffering/timeout** — YES, this is the delivery mechanism of the failure. Confirmed indirectly but strongly: backend completes, frontend would *error* on a clean close, so an infinite spinner = a silent stream held open by the edge. The trigger is the Claude path's lack of keepalive during long prefill gaps.
2. **Prod secret / model / outbound issue** — NO missing/blank secret. Anthropic outbound succeeds (token usage recorded). The only relevant secret difference is `ASSISTANT_PROVIDER=anthropic` (vs `openai` in preview), which routes to the under-built path. OpenAI-key exhaustion is a red herring here (path unused; key re-activated 15:35).
3. **Which build is live / pod health** — active run `7f7efa49` is healthy and serving; it processes these stream requests to completion. Not a build/pod problem.

---

## Recommended fixes

### A. Code (E1) — primary, robust fix
1. **Add an SSE keepalive to `run_chat_claude`** (mirror the OpenAI path). Wrap the `chat.stream_message(...)` async iteration so that whenever no event arrives within ~8s, it `yield`s a heartbeat (`{"type":"ping"}` or an SSE comment line `": keepalive"`). This keeps bytes flowing through the Cloudflare edge during the long per-step prefills so the final `done` is delivered. Also send a heartbeat between steps, before each new `chat.stream_message` call.
2. **Fix the quote-draft optimistic-lock conflicts** in `create_quote_draft` / `update_quote_draft` (engines/assistant_quote_service.py et al.). The persistent "modifications concurrentes" failures force many retry steps, inflating duration/token cost and worsening the stall.
3. (Optional) Trim/compact the per-step context in the Claude path (`fold_inputs` re-sends full history each step → 390k input tokens) to cut per-step prefill latency.

*Note:* I could not reproduce the live stream in the sandbox (it needs EMERGENT_LLM_KEY + the Cloudflare edge, neither available to an isolated pod). The above is verified by **source inspection + production DB/trace evidence**, not by re-running the live stream. After the fix, redeploy and verify.

### B. User — provider decision (secret is user-owned)
Decide the production provider in Deployment Panel → Secrets:
- **Keep `ASSISTANT_PROVIDER=anthropic`** → the Code fix (A) is required (the keepalive makes this path edge-safe). Recommended.
- **OR switch `ASSISTANT_PROVIDER=openai`** to use the already-keepalive OpenAI path that was verified in preview — but only if the account's `OPENAI_API_KEY` is valid and funded (it was reported exhausted historically, which is likely why prod was set to anthropic). Note: even on the OpenAI path, a billing/rate failure auto-fails over to the same keepalive-less Claude path, so fix (A) is still the durable solution.
